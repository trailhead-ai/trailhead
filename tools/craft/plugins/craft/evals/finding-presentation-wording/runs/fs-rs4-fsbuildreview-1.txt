### Would build the wrong thing, needs your decision

**`fs-kiln/unload.py:3`** — Should a firing's cool-down come from the firing itself instead of a fixed time per kiln? I recommend yes. Otherwise the board can call a kiln safe to open while it is still too hot. *(raised by: code review)*

The change says the cool-down "depends on how the firing ran, not only on which kiln it was in." The code instead uses one table, `COOL_HOURS = {"large": 18, "small": 10}`, so every large-kiln firing counts as ready after 18 hours, however hot it ran. Say a large-kiln firing ran hotter and needs longer than 18 hours. At hour 18 it goes on the board as ready to unload, and someone opens a kiln that has not cooled.

Fix: each firing would become ready after its own cool-down time, so a hotter firing in the same kiln would stay off the board for longer. This is my estimate from the cited code: about 2 files and 3 functions, mainly `cool_hours` and `unload_time`, plus the record in the test. One caveat: firing records today have only `name`, `kiln` and `fired_at`. The new field has to come from whoever creates the records, presumably the technician, so that source needs to change too.

### Would cause trouble later, worth fixing, your call

**`fs-kiln/unload.py:17`** — A firing whose cool-down ends exactly at the current minute is left off the board. The change says it should appear, so I recommend counting it as ready. *(raised by: code review)*

The comparison uses strictly-less-than. A firing that finishes cooling at exactly 9:00 is therefore missing from the 9:00 board and appears only on a later one. The change says a firing that cools at this exact minute appears as ready.

Fix: `if unload_time(firing) <= now:` in place of `if unload_time(firing) < now:` in `ready_firings`, so a firing that cools at the current minute counts as ready.
