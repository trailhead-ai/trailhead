These four findings were still open after the one allowed re-review round, so they come to you now. The build has no further fix round. Each one is a place where `fs-kiln/unload.py` still doesn't do what the committee asked for in `change.md`.

## Would build the wrong thing, needs your decision

**`fs-kiln/unload.py:3`**, raised by code review

You need to decide where a firing's cool-down time comes from. I recommend storing it on each firing record. As built, a hotter firing can be listed as ready while the kiln is still too hot to open.

Worst case: the committee said cool-down depends on how the firing ran, not only on which kiln it was in. The code looks it up in a fixed table by kiln (`large` is 18 hours, `small` is 10). So a long, hot firing in the small kiln shows "ready to unload" after 10 hours, and someone opens it early.

Fix: each firing would wait its own cool-down before it appears on the board, and the per-kiln table would go away. My estimate, from the cited code, is about 2 files and 2 functions, chiefly `unload_time` and the `COOL_HOURS`/`cool_hours` lookup. Caveat: the firing records currently hold only `name`, `kiln` and `fired_at`. Whatever creates those records would need to start recording the cool-down too.

## Would cause trouble later, worth fixing, your call

**`fs-kiln/unload.py:17`**, raised by code review

A firing whose cool-down ends exactly at the current minute is left off the board. I recommend counting it as ready, as the committee asked.

Worst case: a firing's cool-down ends at 09:00 and the board is built at 09:00. The check is a strict "earlier than now", so that firing is missing from the board until the next time the board is built.

Fix: `if unload_time(firing) <= now:` instead of `if unload_time(firing) < now:`, so a firing that cools at this minute counts as ready.
