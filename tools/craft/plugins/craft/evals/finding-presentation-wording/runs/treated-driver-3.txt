**Would build the wrong thing, needs your decision**

**1. How the queue keeps order.** Should the queue be ordered by join time instead of a stored position number that is renumbered on every leave? I recommend join time, because the current design can offer one plot to two people.
Worst case: someone leaves at 02:00 while the offer job is reading the queue. Two people are briefly both first in line, and both get an offer email for the same plot.

*Raised by: buildability, failure cases*

**2. A safe way to run the paper-list import.** Should the one-shot import get a preview and an undo? I recommend both, because a mistake here corrupts the real queue for all 340 people.
Worst case: the warden runs the import twice, and every person appears twice. Or the run stops halfway with no record of where it stopped, and there's no clean way to remove what it wrote.
Fix: import under a batch id, show a preview first, and allow a bad batch to be deleted in one go. At this spec's production level this counts as migration and backfill, which is rated Critical.
*Raised by: failure cases*

**3. Knowing when the nightly offer job didn't run.** Should a failed 02:00 run alert someone? I recommend yes. Otherwise, "the person at the front of that site's queue is sent an offer by email" (AC2) quietly stops happening.
Worst case: the job fails for a week, no offers go out, and the first anyone hears of it is complaints from people waiting.
Fix: email the warden when the job finishes, and send an alert if it hasn't finished by 03:00.
I raised this one level from the reviewer's rating: production failure visibility is Critical at this spec's production level.
*Raised by: failure cases*

**Would cause trouble later, worth fixing, your call**
