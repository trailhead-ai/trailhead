**My recommendation: a shared base file plus a small override file per environment.** Add one supporting piece: CI renders the merged config for each environment and shows it in the PR. Here's how the three options compare on diffs and merge collisions.

### How they compare

| | One big YAML | One file per env in `conf.d/` | Base + overrides |
|---|---|---|---|
| **Collision rate** | Highest. Everyone edits the same file, and edits to neighbouring lines in different sections still conflict. | Lowest for changes to one environment. | Low. Environment-specific edits land in small separate files. Only edits to shared settings meet in `base`. |
| **Changing a setting every environment uses** | One edit, but in the busiest file. | N near-identical edits. Each one can conflict, and it's easy to miss one. | One edit in `base`. |
| **Diff clarity** | Hunks are deep in nested indentation, so it's hard to tell which environment a hunk belongs to. | Clear per file, but copy-paste between files hides what is really different. | An override file *is* the list of differences. A one-line diff means a one-line difference. |
| **Drift risk** | Low | **High**: the files slowly diverge in ways nobody intended. | Low |
| **Main weakness** | Collisions and noisy diffs | Duplication and drift | No single file shows an environment's full config, and a `base` edit silently affects every environment |

Per-env files look best on merge collisions, but they only win for changes that touch one environment. A setting all environments use turns into N edits, and N edits mean N chances to conflict or drift. Base + overrides has almost the same isolation for changes to one environment, and a shared change stays one edit.

### Fixing the weaknesses of base + overrides

1. **Render and diff in CI.** For each environment, merge `base` with its override and commit or print the result. In the PR, show the diff of that merged result. Reviewers then see "this `base` change alters prod and staging" explicitly, instead of guessing.
2. **Write down the merge rules.** Maps deep-merge. **Lists replace the whole list; they are not appended to.** Append rules are the usual source of surprises. Don't use YAML anchors or aliases across files.
3. **Keep overrides small.** If an override grows past a screenful, the setting probably belongs in `base` with a different default. If no two environments share a value, the setting probably doesn't belong in `base` at all.
4. **Make diffs easy to read:** sort keys within each map, put one setting per line, and avoid flow style (`{a: 1, b: 2}`). Two people adding keys then usually touch different lines.
5. **Assign owners** with CODEOWNERS on `overrides/prod.yaml` and similar files. Because each environment has its own file, ownership is easy to set up.

Layout:
```
deploy/
  base.yaml
  overrides/
    dev.yaml
    staging.yaml
    prod.yaml
```

### When I'd choose something else
- **Per-env files:** when environments share very little config, or are run by separate teams who shouldn't touch each other's settings.
- **One big file:** with two or three environments and a small team, where collisions don't happen often enough to matter.

One question decides it: **how much of your current config is the same across environments?** If most of it is, use base + overrides. If little of it is, use per-env files. If you share the current file, I can work out that ratio and draft the split.
